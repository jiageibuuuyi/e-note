# ADR-0001：Windows 本地桌面应用架构

日期：2026-10-23

状态：Superseded by [ADR-0002](0002-cross-platform-desktop-architecture.md)（原提议已被替代，尚未按本方案实施）

替代原因（2026-10-23）：用户明确 macOS 和 Linux 为确定的后续平台，原“仅 Windows”前提失效。下文保留历史判断，不作为当前选型依据。

## 背景

用户已确认第一版支持 Windows 10/11，个人本地使用，人员字段仅为姓名，不需要账号和同步。主面板需支持置顶、真正的桌面模式及隐藏到托盘，并具备任务、笔记、附件、日期提醒与历史日历。

工程目录当前没有既有代码。主要约束是常驻资源开销、Windows 系统集成、数据与附件可靠性。“显示桌面后仍可交互”是首要技术验证点。

## 候选方案

1. C# + WPF + SQLite。
2. Tauri + Web UI + Rust + SQLite。
3. Electron + Web UI + SQLite。

WPF 仅支持 Windows，符合已确认平台范围；Tauri 在 Windows 使用 WebView2；Electron 使用 Chromium 多进程架构。框架机制参考 [WPF](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/)、[Tauri](https://v2.tauri.app/reference/webview-versions/)、[Electron](https://www.electronjs.org/docs/latest/tutorial/process-model)。对资源与开发成本的优劣排序是项目判断，需要同等原型测试，不能直接推导具体内存或包体。

## 提议

采用 C# + WPF 的本地分层单体，SQLite 作为单一结构化数据存储。选择满足目标 Windows 版本且仍在支持期的 .NET LTS，并在开工时固定版本。

界面采用 MVVM，统一经应用服务执行操作。规则层处理名称生成、校验、排序、日期语义及状态转换，不依赖 UI 或 Win32。单一仓储实现封装参数化 SQL；系统行为集中在 Windows 适配层。附件服务管理文件副本、导入状态和迁移。

不增加独立后端服务、本地 HTTP 端口、第二套数据访问方式或常驻后台服务。模块通过进程内调用协作。

## 结果与成本

- Windows 窗口、托盘和文件集成有明确实现边界，适合当前限定的平台目标。
- 本地数据操作无需网络，归档与日历共享同一数据源。
- 开发者需要 C#/XAML 和必要的 Win32 调试能力。
- 桌面宿主集成仍需维护兼容性，并非采用 WPF 后自然解决。
- .NET 分发方式影响安装体积；安装器与运行时一并计量。
- 未来跨平台需要替换系统适配和界面层；当前不为未确认需求引入跨平台复杂度。

## 验证与重新评估条件

1. 先制作窗口原型，实测桌面模式的可见性、点击、双击、中文输入、拖入文件、多显示器、DPI、Win+D 和 Explorer 重启。
2. 在明确设备和 Release 环境测量启动、空闲 CPU、常驻内存、安装体积；预算见项目计划书第 8 节。
3. 构建或架构测试检查规则层不引用 WPF/Win32，界面不直接执行数据库和附件写入；违规逻辑移回应用服务与适配层。
4. 自动化测试覆盖日期边界、排序、状态转换；集成测试覆盖文件导入中断、数据库迁移与完整备份恢复。
5. 桌面模式不满足已确认目标时，记录具体失败条件并评估替代实现；普通窗口置底不作为等价验收结果。
6. 团队技术能力、平台范围或资源实测结果改变时，新建 ADR 记录替代方案，不悄悄引入第二套架构。
