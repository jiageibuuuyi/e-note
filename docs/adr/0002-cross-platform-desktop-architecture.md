# ADR-0002：跨平台界面、系统适配与本地数据架构

日期：2026-10-23

状态：Proposed（提议；用户已确认跨平台目标，具体框架待原型验证）

2026-10-25 开发交接：按本方案编写[开发实施指南](../开发实施指南.md)，数据契约细化见[ADR-0003](0003-development-data-contracts.md)；尚未进行框架及平台原型验证。

替代：[ADR-0001](0001-windows-local-desktop-architecture.md)。

## 背景与决策因素

Windows 10/11 是首发平台，macOS 与 Linux 是后续必须支持的平台。产品为个人本地使用的轻量桌面任务/笔记工具，包含真正的桌面模式、托盘、原文精准搜索、动态继承子任务、文件及整个文件夹移动、复制/剪切粘贴。

原 WPF 提议没有实施代码，现阶段可以调整框架，不承担既有界面迁移成本。需要复用主要界面和业务规则，并对系统能力差异、可恢复文件操作、路径可迁移性负责。

## 候选与提议

首选 **C# + Avalonia + SQLite**。共享 UI 使用开源 Avalonia 与 MVVM；业务核心独立于 UI 和操作系统；Windows/macOS/Linux 原生行为由各自平台适配层实现。WPF 不再是主界面方案，也不计划依赖商业 WPF 兼容层。

Avalonia 支持三类桌面平台并提供跨平台 UI 架构；具体系统版本的支持等级不同。[官方平台矩阵](https://docs.avaloniaui.net/docs/supported-platforms) · [官方架构](https://docs.avaloniaui.net/docs/fundamentals/cross-platform-architecture)

Tauri 是主要备选，适用于团队以 Web/Rust 为主要技能或原型实测证明更适合的情况；仍须系统适配及 WebView 差异测试。Electron 的多进程模式需要重点审查常驻资源预算。本提议不声称 Avalonia 必然比所有备选更省内存。[Tauri WebView](https://v2.tauri.app/reference/webview-versions/) · [Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)

## 共享边界

- 共享：主要界面、任务/笔记操作、搜索、子任务继承、日期判定、排序、日历、SQLite 仓储、附件作业状态机、备份格式。
- 平台适配：桌面层级/位置、系统托盘或菜单栏、通知、登录启动、快捷键、剪贴板文件及剪切意图、文件身份/锁、文件管理器交互。
- 共用工程不引用 Windows 专用目标框架；规则层不引用 Avalonia 或任何原生系统 API。UI 不直接写数据库或执行源文件删除。
- 单一 SQLite 访问层负责事务与数据库迁移，使用统一应用服务写入。不存在服务器或常驻后台服务。

## 重要数据约束

1. 子任务使用 `parent_id` 及逐字段覆盖标志。未覆盖动态跟随；独立空值不等于继承。完成快照冻结历史有效值，重新打开恢复求值。
2. 搜索使用字段原文的字面量连续包含语义，不以分词、通配符或模糊匹配替代；查询参数化，子任务使用实际生效值。
3. 附件记录使用根目录 ID 与相对路径，跨平台恢复重新映射目录并处理大小写/文件名冲突。
4. 拖入移动，复制粘贴复制，剪切粘贴移动；操作意图持久化，无法识别剪切时不猜测删除源项。
5. 同卷快速移动使用预写日志，跨卷先复制校验并登记再清理源项；源清理失败有独立状态。文件夹清理按验证清单执行，不递归强删源树。
6. 文件系统操作与 SQLite 不构成同一事务，必须有逐项作业日志、幂等重试、故障恢复和对账。
7. 跨设备恢复不重放导出机器上的删除源文件动作。备份覆盖文件夹、子任务继承、完成快照及所选回收范围。

详细产品规则以[项目计划书 V0.2](../../桌面待办与笔记应用_项目计划书.md)为准；未确认的继承字段范围和生命周期细则仍标为提议。

## 系统能力边界

Windows 真正桌面模式仍须验证 Win+D 后可见与可操作。macOS 需验证桌面层级与 Spaces；Linux 区分发行版、桌面环境、X11/Wayland。框架能运行不代表支持所有窗口行为。

Avalonia 官方当前将原生 Wayland 后端描述为尚有能力差异的可选后端；文件剪贴板能力亦可能因 Linux 桌面环境不同而变化。[Linux 后端说明](https://docs.avaloniaui.net/docs/platform-specific-guides/linux) · [剪贴板平台说明](https://docs.avaloniaui.net/docs/how-to/clipboard-how-to)

适配层报告能力状态，平台范围定稿时明确无法达到的行为及经确认的替代方案；不可将普通置底默认为真正桌面模式已通过。

## 验证与重新评估

- 首阶段完成 Windows 桌面交互原型及资源基线，并在 macOS/选定 Linux 环境运行冒烟验证；没有真实环境的项目标“未验证”。
- 构建检查共享工程无 Windows 依赖，规则层无 UI/系统引用；违规调用移回适配层，不建立第二套并行实现。
- 业务测试覆盖逐字段继承、独立空值、同值覆盖、恢复继承、日期冲突、精准搜索和完成快照。
- 使用临时测试数据故障注入文件移动各阶段，验证源目标完整性及恢复；不使用用户真实文件进行破坏性试验。
- 三平台分别锁定 SDK、Avalonia 和系统版本矩阵，分别测量打包、启动、CPU 和内存；所有性能数字都是待测预算。
- 若 Avalonia 在目标平台的必需能力或实测资源上不满足约束，制作同等 Tauri 原型后更新 ADR，保留共享规则与数据契约。

## 成本与后果

主要 UI 和规则可以在三个系统复用，避免 Windows 完成后再重写整套界面。代价是早期必须投入平台能力验证，后续仍需三端打包、系统适配与运行测试。Mac/Linux 正式发布是独立里程碑，不能包含在 Windows V1 的完成声明中。
